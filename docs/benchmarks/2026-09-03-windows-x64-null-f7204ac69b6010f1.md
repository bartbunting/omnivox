# Windows x64 Null-output Pre-optimization Baseline, 2026-09-03

This is the frozen baseline immediately before the planned TGSpeechBox and
streaming work. It measures a post-v1.6.4 development build and is not evidence
about the published v1.6.4 artifact.

## Scope and provenance

- Target: `x86_64-pc-windows-gnu`, run through Windows interoperability from
  WSL2 on `Linux-6.18.33.2-microsoft-standard-WSL2-x86_64-with-glibc2.43`.
- Server version: `1.6.4`.
- Server build ID: `f7204ac69b6010f1`.
- Server and benchmark-harness Omnivox commit:
  `2973d5efc86d40520f146bd635209e40b4154c9e`.
- Emacsvox deployment commit:
  `3c47d0a2afa46ad4c9a32a5215bcddc4e7bdb019`.
- Toolchain: Rust `1.97.1`, Python `3.14.4`, MinGW GCC `12-win32`,
  and MinGW G++ `13-posix` for TGSpeechBox.
- Engines and representative voices: WinRT David, eSpeak NG US English,
  RHVoice SLT, Flite SLT, RuTTS male, DECtalk Paul, Eloquence `v1`, and
  TGSpeechBox Adam.
- Runtime provenance: DECtalk used the bundled pinned archive; RHVoice and
  Eloquence used external, user-supplied runtimes; TGSpeechBox used the
  experimental WSL-host development companion.

These are all eight physical engines in the configured payload. `native` is a
routing alias realized as WinRT, not another engine. Piper was not included
because this deployment has no configured model. This is an engine-level
comparison using one pinned physical voice per engine, not an all-voices test.
The exact IDs are retained in the plan and raw reports.

The payload labels itself `local-dirty-worktree` because the supported
development build path permits local changes. Its recorded Omnivox and
Emacsvox tracked-worktree hashes are both the SHA-256 empty-diff hash, so the
staged source matched the commits named above.

## Method

The [suite plan](plans/2026-09-03-windows-x64-null-f7204ac69b6010f1.json)
used seed `20260903` to randomize the engine-block order. It ran 20 recorded
iterations for each of six cases: character, word, line, dense-action
timeline, multipart timeline, and rapid keyed replacement. Each engine has
cold and warm groups, producing 240 recorded winner samples per engine and
1,920 in total. Cold mode started a new server for every sample. Warm mode
reused one server and ran two unrecorded warmups before each case.

The replacement case sent five dispatches. All 320 recorded replacement
winners completed, and every one observed the other four dispatches cancelled:
1,280 verified stale cancellations in total. Every recorded winner used its
expected engine and exact physical voice. DECtalk and Eloquence were selected
through the public runtime routing policy, with no fallback engine configured.

Omnivox ran with `--audio-output null`. No samples were played. Measurements
use Python's `time.perf_counter_ns`. Dispatch-to-source ends when the client
receives the first `utterance_started` null-source marker; terminal timing ends
when it receives the tracked terminal record. Terminal results therefore
exclude waveform playback duration. Neither boundary measures physical
acoustic onset or audio-device latency.

eSpeak NG, RuTTS, and Eloquence form the fastest warm group in this null-output
run. TGSpeechBox has both the highest warm source latency and the largest
source-to-terminal gap on dense and replacement work, making it the clearest
target for the planned response and streaming changes. Cold process startup
remains material for every engine, especially TGSpeechBox. RHVoice's cold
character group contains a 454.887 ms dispatch-to-source p99 outlier; it is
retained rather than removed.

## Limitations

- Null output intentionally excludes waveform duration, audio-device
  buffering, underruns, and physical acoustic onset. Its terminal timings are
  not comparable with device-output terminal timings in the earlier baseline.
- Engine blocks were randomized, but there is only one block per engine, so
  host drift can still influence cross-engine comparisons.
- Twenty samples per group characterize this development machine, not every
  Windows system or runtime installation.
- Only one representative voice per engine was exercised. This does not
  replace the separate two-voice RuTTS acceptance evidence.
- External RHVoice and Eloquence installations cannot be reconstructed from
  this pack alone, although the available hashes and configuration labels are
  retained.
- The TGSpeechBox adapter remains experimental, has no speech markers, and was
  built by the WSL-host development path.
