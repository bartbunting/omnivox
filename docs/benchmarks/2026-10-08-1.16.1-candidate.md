# Omnivox 1.16.1 patch candidate

Candidate source: `69ae85a080dc026454a31cbd4f8b6a9af4954afd`, prepared on
2026-10-08 from published `v1.16.0`. The runtime change is the eSpeak marker
ordering fix from `0890499` (development commit `65e86a0`). The branch also
retains the previously accepted Homebrew release-completion checks. Later
engine-configuration editing, named punctuation profiles and helper write
deadlines are outside this patch release.

## Reproduction and fix

[Emacsvox issue 7](https://github.com/bartbunting/emacsvox/issues/7) reports a
Markdown list line stopping after its first few words. Captured submissions
contained the complete line. Omnivox failed while streaming eSpeak output with
`progressive engine markers are out of order`.

At faster speech rates, word markers in adjacent native callbacks can overlap
in time. Sorting each callback separately did not order the complete stream.
The adapter now retains future markers until their PCM window is ready, then
emits them in timestamp order before that audio. It preserves the native
timestamps and bounded streaming. The native regression fails before the fix
at rate 0.85 and passes with the fix at rates 0.5 and 0.85.

The retained Windows 1.16.0 comparison completed one of three readings and
failed the other two with the marker-order error. Its executable SHA-256 is
`85bf9759de977b6e41fbe8365e15207a81feda306032f89f874466a7b1089993`.

## Build environment

The fresh checkout needed its pinned native inputs prepared first. Piper's
eSpeak phoneme compiler then truncated a path under the longer checkout name.
The successful workspace checks used `CARGO_TARGET_DIR=/tmp/ov1161.yFxF9E` and
`OMNIVOX_PIPER_INPUTS_DIR` pointing to the verified native inputs in the release
checkout. No source or dependency changes were needed.

The Windows container build could not resolve the linked worktree's Git
metadata. Its retry uses a standalone clone of the same source commit. The
failed build logs are retained alongside the successful checks.

The Windows candidate uses the pinned GNU build, while the published 1.16.0
comparison uses the release's MSVC build. These are functional checks, not
compiler-matched performance measurements.
